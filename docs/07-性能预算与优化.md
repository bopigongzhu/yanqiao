# 07 · 性能预算与优化

## 1. 能否现在说会占多少内存和 CPU

2026-10-08 的 0.2.5 已完成一次 5 分钟浮窗移动、跨屏、真实 Direct2D 绘制与重建拼音组合的合成负载。辅助进程预热后约 **61.34–61.60 MiB Private Bytes**，采样最大工作集 **49.10 MiB**；本机 16 逻辑处理器上平均 CPU **0.131%**。与自有原生试用宿主合计平均 CPU **0.183%**。该测试未计入真实软件中的 TSF 增量或云端请求，不能代替完整资源验收。详细口径与分页对比见 [0.2.5 资源报告](../verification/native-0.2.5/performance.md)；[0.2.4 旧报告](../verification/native-0.2.4/performance.md)保留。

同版本无界面、未主动绘制的集成样本约 **4.27 MiB Private Bytes / 19.43 MiB Working Set**，10 秒空闲期未记录 CPU 时间增量。两种负载条件不同，不能用无界面低值代表显示浮窗后的实际占用。下文数字仍是**工程预算与验收方法，不是最终保证**。

DeepSeek 在云端完成模型推理，本机不加载大语言模型，也不需要为翻译占用 GPU 显存。本地主要开销来自全拼词典、输入服务、文字绘制、辅助进程、HTTPS 与短期缓冲。浏览器原型包含浏览器自身的进程和渲染开销，不能用它推算最终输入法占用。

目标是日常常驻时几乎不消耗 CPU，打字时不阻塞前台软件，多窗口使用时避免无界增长。不能为了降低任务管理器的某个数字而破坏响应速度或重复释放、重新加载词典。

## 2. 参考环境与统计口径

预算参考机：Windows 11 x64、4 核 / 8 逻辑处理器、16 GiB 内存、SSD、普通桌面分辨率。记录实际 CPU 型号、系统版本、DPI 和电源模式；其他硬件另测，不直接横比百分比。

### 内存

主要预算指标为 **产品可归因的总增量 Private Bytes**：

```text
产品增量私有内存
  = Companion 私有提交量
  + 各测试宿主启用本输入法前后可归因的私有提交增量
  + 本产品其他常驻进程私有提交量
```

单位使用 MiB（1 MiB = 1,048,576 bytes）。同时报告 Private Working Set、完整 Working Set 和峰值，不能把提交量当作全部已驻留物理内存。共享词典映射页可能被多个进程工作集重复统计，应由 VMMap / ETW 检查归属，不能简单相加后宣称物理内存占用。

真实应用本身会分配内存。基线先用可控的测试宿主和固定操作重复 3 次，再在记事本、Edge、微信等应用做补充观察；不能把浏览器自己新建标签页的内存算到输入法里。

### CPU

CPU 百分比按整台机器的逻辑处理器总能力归一化，接近任务管理器口径：

```text
整机归一化 CPU % = 产品相关 CPU 时间增量 /
                   (采样墙钟时间 × 逻辑处理器数量) × 100
```

另列单核等效百分比：`整机归一化值 × 逻辑处理器数`。例如 8 线程机器显示 2%，相当于平均占用 0.16 个逻辑核，而不是 2% 的一个核。宿主内 TSF 线程通过 ETW 堆栈或受控基线差分归因。

## 3. 起始资源预算

以下表格是设计目标，当前每一项的实测状态均为 **待测**。

| 场景 | 总增量 Private Bytes 目标 | 整机平均 CPU 目标（8 逻辑处理器） | 观察窗口 |
|---|---:|---:|---|
| 仅辅助进程待命（当前启动时即初始化引擎） | ≤30 MiB | ≤0.1% | 稳定后 60 秒 |
| 已在 1 个宿主使用并返回空闲 | ≤80 MiB | ≤0.1% | 稳定后 60 秒 |
| 1 个宿主持续全拼输入 | ≤120 MiB | ≤1.5% | 持续输入 60 秒 |
| 1 个宿主持续翻译、偶尔展开讲解 | ≤120 MiB | ≤2.0% | 持续操作 60 秒 |
| 3 个宿主都已启用，只有 1 个在输入 | ≤180 MiB | ≤2.0% | 稳定后 60 秒 |
| 连续使用 8 小时后回到相同空闲状态 | 相比热身基线净增长 ≤10 MiB | 返回 ≤0.1% | 每小时取样 + 结束观察 |

短暂启动 / 词库初始化可超过平均预算，但不能卡住宿主。额外目标：稳态运行时整机 CPU 的短峰超过 10% 不持续 200ms 以上；启动峰值单独报告，不能被长时间平均稀释。

初步分配约束：

- 纯 TSF 桥接层在尚未加载词典时，单宿主增量争取 ≤3 MiB。
- 浮窗、网络客户端、设置和调度共用一个用户辅助进程，不为每个宿主额外启动一个。
- 词典加载的私有页是主要不确定项，必须在 M1 实测；若一份词典就使预算不成立，调整词库和加载设计后再继续。
- 当前会话的中文、候选、英文与讲解实际文本很小；其全部应用层缓冲预算 ≤1 MiB，不应发展成无界队列。
- 不为达标主动调用工作集修剪接口制造“数字变小”的假象；这可能使后续按键触发分页并变慢。

## 4. 架构层优化

### 4.1 使用原生 UI

本次将发行版首选界面改为 C++ / Win32 / DirectWrite / Direct2D，避免为一个小型输入浮窗常驻浏览器运行时或托管桌面运行时。设置窗口按需创建，关闭后释放控件与图形资源；共享字体、画刷等小型资源按生命周期复用。

这属于降低基线的设计方向，不意味着已经证明原生实现一定低于某个数值。仍需比较候选实现的可访问性、字体渲染、维护成本和实际资源占用。

### 4.2 词典与宿主进程

- 当前实现将引擎集中到单辅助进程；每宿主只加载轻量桥接 DLL，多宿主共享一个活动句子会话。
- 只在真正启用本输入法时懒加载引擎，不按每个打开窗口建立词典副本。
- 词库默认只读，优先采用引擎已有的文件映射 / 数据复用能力。不要未经验证就声称 librime 已跨进程共享全部内存。
- 识别哪些页可由系统共享、哪些是私有反序列化索引；词典大小与私有增长必须分别记录。
- 已采用集中式引擎；超预算时继续测量桥接线程、IPC、词典索引与 UI 的成本，避免以搬移进程代替减少总占用。

**集中引擎的代价**：跨进程按键与候选响应、宿主故障恢复、顺序与延迟会变复杂。当前已有有界队列、按键序号和自动重连；主动退出后暂停自动启动，崩溃后的未提交草稿仍不能恢复。需要实际宿主验收，不能漏算辅助进程内存后宣布总成本达标。

### 4.3 事件驱动调度

- 无输入会话时停止周期计时器；等待输入事件、IPC、网络完成或系统通知。
- 0.2.4 的位置跟随在活动草稿期间增加 100 ms 检查，配合布局事件；事件触发的读取至少间隔 50 ms，同一时刻最多一个未完成异步读请求。纯位置变化不触发翻译，草稿结束后停止位置检查。
- 500ms 最短翻译间隔只对活动输入生效。每次只留 1 个活跃请求 + 1 个最新 pending，不排队保存所有中间句子。
- 不创建每按键一个线程。输入服务、异步 IPC、WinHTTP 后台工作线程、UI 线程各司其职；当前 WinHTTP 不是回调式异步模式。
- UI 更新只在候选、文字、位置或状态变化时失效绘制，不以 60 FPS 持续刷新静止面板。
- 流式 token 合并成最多每 33–50ms 一次的 UI 更新；只重排变化的文字区域。
- 状态动画尊重减少动画设置；隐藏浮窗、会话结束时停止全部动画与光标定时器。

### 4.4 网络与字符串

- 复用 WinHTTP session 和允许复用的连接，不为每次快照重复创建完整网络栈。
- 对源文做精确版本 / hash 去重；光标移动和纯 UI 操作不请求翻译。
- 限制源文 300 字、翻译输出预算 384 token、讲解最多 3 项；响应体还需字节级上限，建议翻译 16 KiB、讲解 32 KiB。
- UTF-8 分片解析复用缓冲并校验边界，避免逐字符复制整个累计文本。
- 讲解只有用户展开才请求，新源文出现即取消旧讲解；异常重试有次数上限。
- 会话结束释放草稿、讲解、结果与 pending；不使用无界内存缓存，也不写磁盘历史。

## 5. 测量流程

1. 在干净 Windows 11 测试机记录机器信息、空闲基线与测试版本。
2. 安装输入法但未启用，观察常驻进程、线程、句柄、网络连接和计时器。
3. 在可控宿主启用并预热 2 分钟，记录引擎加载前后 Private Bytes、Working Set、共享页。
4. 按表格逐项执行 60 秒场景；输入用固定合成脚本与真实人工操作各一轮。
5. 记录单宿主与 3 宿主切换成本。另增加 10 个宿主的压力实验，报告增长曲线，即使它不属于主预算场景。
6. 测试关闭浮窗、取消草稿、切换输入法、关闭宿主后内存和定时器是否按设计回收。
7. 每秒采集资源计数；对短 CPU 峰使用 100ms 采样或 ETW 分析。不能用 1 秒采样证明 200ms 峰值条件。
8. 使用 Windows Performance Recorder / Analyzer 定位 CPU、分配和唤醒热点；VMMap 分析词库映射与私有堆；Process Explorer 辅助观察。
9. 进行 8 小时耐久测试和 1,000 次打开 / 关闭讲解、设置、切换上下文的循环，检查内存趋势、句柄、线程和 UI 资源。
10. 生成不含真实用户文本 / Key 的报告，列出未达预算项目和优化前后同条件对比。

不得在测试前清空操作系统缓存、禁用其他进程或修剪工作集后只挑最小值宣传。测试中的控制条件应公开记录。

## 7. 与“1 秒翻译”的取舍

刷新越频繁，CPU 不一定大幅增加，但网络请求数、费用和过期结果会增加。应在完整翻译延迟、内容新鲜度、费用和本地消耗之间一起评估，不能只追求动画看起来快。

本地目标是确保中文按键路径不等待网络（p95 建议 ≤30ms），空闲不轮询，持续更新可控。云服务实际响应如果超过 1 秒，增加本机 CPU 占用通常无法解决；应优化请求规模与连接、测量服务端表现，而不是提高本地刷新频率。

首个真实可执行版本完成后，必须用上述流程给出“实际占用多少”的答案，并将本文件中相应项目由“待测”更新为实测数据。
